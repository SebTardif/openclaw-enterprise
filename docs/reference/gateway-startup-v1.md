# Protected Installation Gateway startup

The Gateway startup components define and implement a separate Installation process
boundary. They retain an original startup operation and process generation, a
separate provider-create submission, and a recipient consume before local host
startup. They do not turn an Agent Runtime assignment or Namespace Harness context
into Installation authority.

The neutral types are exported from
`@openclaw-enterprise/contracts/gateway-startup-v1`. The owner command body is
exported from `@openclaw-enterprise/occ/gateway-startup-v1/owner`. The PostgreSQL
backend and schema factory are internal original-owner collaborators. The local
Gateway lifetime and dedicated Installation service router are internal trusted
composition; public object data cannot construct their enrolled handles.

The actual production account/security and accepted-selection participants,
private central transaction binding, authenticated Installation bootstrap,
protected material/path source and physical-settlement reader are still required.
Missing participants return unavailable or deny before accepting work. The
zero-argument Gateway startup reader does not gain a production authority source
from these definitions or controlled fixtures. No runtime image, provider,
registration or database is started by importing these components.

## Original command and transaction

An accepting operation includes its immutable command reference, expected head,
selected definition and predecessor-disposition reference. The original owner
holds account/security, IAM and selected-definition currentness before locking
the Installation startup head. It then validates the exact old head and physical
predecessor disposition before allocating a new process and create effect. A
complete initial disposition is real protected evidence; an empty startup table
is only empty storage.

`processGeneration` belongs to this Installation process. `hostRuntimeGeneration`
is the separately selected native host operand. The full binding also retains
configuration/profile references and versions, admitted revision, assignment,
native configuration reference/digest, state ownership, schema/protocol versions,
ordered selected modules/capabilities and existing startup/shutdown deadlines.
An equal digest alone cannot replace the original selection or material
correspondence. No credentials or native configuration contents are stored in
this binding.

| Command           | Retained effect and result                                                                                                    |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `accept-startup`  | New original startup, process generation, create effect and mandatory audit after expected-head and predecessor checks.       |
| `submit-create`   | One original provider submission, separate from recipient consume. A prior submission requires recovery.                      |
| `consume-startup` | One original recipient/process-incarnation claim, after retained create submission and actual current recipient checks.       |
| `read-current`    | Exact current consumed startup, selected binding and original recipient. An old record does not satisfy it.                   |
| `withdraw`        | A retained withdrawal of the original head; process/create identity remains available to its independent cleanup owner.       |
| `read-operation`  | Separately authorized historical readback of the exact original command. It grants no new submission, consume or current use. |

The original transaction owner supplies `GatewayStartupOwnerPhaseV1`, its actual
`RepositoryTransactionLifetime`, private policy view and tracked query. The
command enters that lifetime once. Collaborator operations use the accepted
phase query without reentering outward repository admission. Caught, chained or
unawaited failures poison the complete command. Admissions close before draining;
accepted query work and invalid asynchronous fence settlement remain owned.
Currentness functions must return exactly `undefined` synchronously.

Audit, immutable event and explicit head CAS use the same client. A provisional
callback result is not success: only actual COMMIT acknowledgement after final
fences and terminal cleanup returns an accepting result. Unknown COMMIT retains
its original command locator for readback. A retry cannot allocate another
operation or repair an uncertain predecessor. The startup phase does not join
credential, profile, lifecycle or journal phases, create another barrier, or
borrow their authentication handles.

The two startup tables preserve original Installation and audit parent objects,
unique operation/generation/process/create-effect/audit identities, separate
submission/consume uniqueness and closed stored core correspondence. The matching
forward database guard layer makes events immutable, validates each head
transition and checks final head/history consistency at COMMIT. The backend owns
no pool, transaction or connection teardown. SQL checks do not authenticate an
account, validate a physical receipt or replace the full source decoder.

## Private submission and local host lifetime

A provider ticket exists only after a newly committed exact `submit-create`.
Its original owner captures the complete create input and protected process-call
instance, then consumes the private ticket synchronously once at the provider
boundary. Unknown COMMIT, a retained submission row, a copied ticket or a changed
call/input cannot authorize another provider submission. Currentness remains a
mandatory original protected call capability.

The bootstrap authenticates the actual Installation service and completes one
confirmed durable `consume-startup` before enrolling the local Gateway pair.
Local `start(recipient, startup)` consumes only that same-instance private pair.
It fresh-reads the already consumed original claim, rechecks currentness and
borrows the selected material. It performs no second durable consume.

The fixed adapter returns a prepared composition before host start. Runtime
retains this prepared handle before any post-await check, then retains the
synchronously returned host before awaiting readiness. Revocation immediately
quiesces the host and invokes the prepared adapter's idempotent cleanup even when
readiness remains pending. That adapter owns host/module cleanup; Runtime does
not independently close the same modules twice. Late material or prepared
results remain owned and are closed before a non-started result returns.

A successful result exposes `lifetime.closed`, which joins local cleanup and late
settlement; awaiting it does not request immediate shutdown. `close()` is
idempotent and joins the same outcome. Cleanup can be finished, failed or unknown.
Every local close result keeps physical `termination: "unknown"`. A pending join
retains ownership instead of reporting completion or permitting a replacement.

## Installation service scope

The dedicated Installation service router recognizes only private invocations
from the fixed genuine native inspector. Its selected profile is
`installation-gateway-startup-v1`, with transport
`owned-child-stdio-installation-gateway-startup-v1`. It permits only
`consume-startup`, `read-current` and separately authorized `read-operation`.
It does not widen either existing Agent service-trust profile or any of the seven
Runtime assignment purposes.

Transport endpoint identity and the startup payload recipient are separate.
The Gateway client has its own Source/SPIFFE identity and authenticates the
Controller peer; the Controller server has its own identity and authenticates
the Gateway peer. The transport recipient remains the Controller. The original
Gateway process/local recipient is retained in the startup association. The
fixed native side selects endpoint semantics; a caller does not choose its role.

Each exchange receives its own exact command/bounds invocation. The same bounded
native connection may support sequential current reads after consume, but
connection loss or its original maximum age closes the enrolled lifetime. A
reconnect does not revive an old invocation. Actual registration, process
incarnation, selected policy and required account/security predicates remain
mandatory inside the original owner transaction. Native authentication alone is
not a current Installation grant.

## Compute process collaborator

The selected Kubernetes Driver's separate Installation participant has six
methods. Its programmatic protected constructor dependencies are required before
Kubernetes access; their presence does not authenticate a caller. Original call
context, recipient, request and deadline remain unchanged. Currentness fences,
absolute and monotonic deadlines surround provider I/O and positive results.

`createOriginal` consumes the exact protected launch plan and Namespace identity,
then an original confirmed submission ticket before one SDK create with retries
disabled. Returned UID/resourceVersion and controller generation are retained
through the original record owner. Late provider settlement remains attached to
that original possible effect after cancellation.

`discoverOriginal` and `recoverOriginal` return `found` for authenticated retained
original correlation. This is not a fresh API existence or running-process
observation. `observeExact` independently checks current Namespace, Deployment,
ReplicaSet and Pod UID ancestry, complete selected lists, controller references,
node/runtime-class and init/main container identities. Multiple applicable
chains remain ambiguous. Known partial and late descendants stay retained with
explicit completeness. Creation resourceVersion is historical; current
observations return fresh resourceVersions.

`requestRetirement` uses independently current original cleanup responsibility,
exact current identity and deletion preconditions with the original selected
policy. A deletion acknowledgement still means termination unknown.
`readReplacementDisposition` consumes an independently authenticated and current
physical-settlement receipt. It must cover the full applicable process tree and
outstanding/late-create closure, or a genuine complete initial disposition.
Neither API absence, host close, container status nor a public Boolean supplies
this missing physical producer.

## Agent Gateway subjects (V2)

The versioned Agent Gateway source uses a closed `agent-gateway` subject containing
`installationId`, `namespaceRef` and `agentRef`. Each head is unique under
Installation and Agent; Namespace is immutable membership, not another head key.
Different Agents may have distinct Gateway heads in one Installation. Independent
Installation services retain their own identities. The historical V1
Installation-only command domain, records and process calls remain separate;
a V2 subject cannot be manufactured by relabelling a V1 call or Agent Runtime
assignment.

The V2 selected binding retains `manifestRef`, `manifestDigest`, `admissionRef`
and `admissionVersion`, the five original role references and
`admittedConfigurationDigest`. Existing `profileRef`/`profileVersion` operands
still name the selected host/module definitions; they are not aliases for those
four selection fields. Original Configuration generation, Agent revision,
process generation and host runtime generation also retain their separate
meanings. The admitted selector accepts the actual V1 or V2 owner unit through
one implementation and fences a V2 subject's full Installation/Namespace/Agent
correspondence. Genuine locked admission and capability participants remain
required; a structurally valid binding cannot supply them.

A new Agent head does not prove that an older Installation-wide process is gone.
The explicit `retired-installation` predecessor bridge requires the authentic
historical V1 withdrawal and independent physical/late-create closure through
the original V1 process reader. That physical predecessor is separate from the
new V2 event chain. Empty V2 storage cannot bypass an unresolved historical
create. Operation, process, create-effect and audit identities remain globally
unique while the generation and head checks respect their versioned subject.

V2 keeps the same six process method meanings with separate typed calls and
submission tickets. The original call owner must enroll the whole invocation
and register its drain before asynchronous accepting, launch-plan or submission
work. That invocation owns deferred assertions, provider settlement and late
retention. It survives the short submission transaction's COMMIT and closes only
at the actual call's terminal settlement. The newly committed submission ticket
is consumed synchronously immediately before the one provider create. No SQL
transaction is held over Kubernetes I/O, and an inner COMMIT does not settle the
outer invocation.

The PostgreSQL owner/backend, V2 schema factory, forward
`0031_gateway_agent_subjects` SQL and original central binding must be composed
together before use. The forward change preserves V1 history and partitions all
four deferred history/head foreign keys and transition guards. The backend also
uses those forward subject columns for historical V1 reads; replacing its code
alone is insufficient. Numbered source or a factory import is not evidence that
a migration ran or that a current participant is installed.

The existing Installation service profile still has exactly its three selected
commands. V2 source types do not add native registration, bootstrap transport,
material delivery or service authorization automatically. The original owners
must bind the exact Agent process, recipient, current admitted selection and
whole-call lifetime to the actual authenticated source. Missing account/security,
admission/renderer/placement/material or physical-settlement participants remain
unavailable. Controlled V2 owner and selector tests qualify source behavior;
they do not establish those production inputs or database execution.

## Verification and current limits

The conformance suites exercise the real owner, phase, private submission ticket,
Installation invocation router and local lifetime with controlled collaborators.
They do not establish genuine account/session/IAM, native TLS, registrar,
protected filesystem material, physical process or Kubernetes behavior.
The strict fixture compiles the supported public subpaths and actual Gateway
host type, including negative caller cases.

After explicit selected dependency preparation, run the three
`tests/conformance/gateway-startup-*.test.mjs` owner/lifetime/Installation-service
files and compile `tests/fixtures/gateway-startup-v1/tsconfig.json`. The separate
`tests/integration/gateway-startup-postgres.test.mjs` requires an explicitly
allocated fresh PostgreSQL fixture and otherwise skips. Its selected body uses
the real owner/phase/backend and pg transactions, while its authority
participants remain controlled; actual central store composition and production
authentication require their own original-owner evidence. No PostgreSQL result
is inferred from pure tests or schema source inspection.
